# Nestjs Jira TG bot

## Что умеет бот
- Создавать баги из супергрупп в вашу Jira (Название топика в супергруппе должно включать ключ проекта)
- Синкать с Github через вебхук и Action и публиковать ссылку на PR в комментариях к задаче в Jira (название ветки или ПР должны включать ключ проекта и номер задачи) (за автора комментария берется пользователь - владелец токена)
- В личке с ботом можно получать таблицы работы по задачам и отображать зарплату по часовой ставке или фиксированной за спринт

## RU
Nest.js телеграм бот, для отправки сообщений и картинок задачами в Jira, сбора таблиц работы над задачами и зарплаты

## EN
Nest.js telegram bot for sending messages and images to Jira, collecting tables of work on tasks and salary

### Development
Для корректной локальной работы, необходимо создать файл .env.dev и заполнить его переменными окружения, аналогичными .env.example, с учетом ваших доступов к проектам в Jira.

Локально проект запускается командой:
```bash
pnpm run start:dev
```

Для деплоя на сервер понадобится настроить Action/Secrets в Github.
Конретно используемые аргументы из env окружения сборки описаны в файле github/workflows/production-deploy.yaml


### Работа в супергруппе

Рабочий чат задаётся через `CHAT_ID`; сообщения отправляются в топик вида `[jira&bot]:key=PROJECT_KEY&type=Bug`. Поддерживаются `Bug`, `Task` и `Story`, по умолчанию — `Bug`. Фото использует подпись как описание, а изображение прикладывается к задаче.

Сотрудник должен быть активен и иметь доступ к проекту в `/admin`; владелец может создавать задачи во всех настроенных проектах. Упоминание `@username` назначает задачу активному сотруднику с доступом к проекту и связью с Jira. Иначе используется Jira-пользователь автора сообщения. После первой миграции включите нужных сотрудников и проверьте проекты, чтобы они могли продолжать создавать задачи из супергруппы.

### Управление через /admin

Отправьте `/admin` в личном чате с ботом. Меню доступно только владельцу с числовым ID из `ADMIN_TELEGRAM_ID`. Username, старый `SUPERADMIN_LIST`, групповой чат и чужие callback-кнопки права администратора не дают.

Один раз задайте в `.env.dev` / `.env`:

```dotenv
ADMIN_TELEGRAM_ID=YOUR_NUMERIC_TELEGRAM_ID
BOT_CONFIG_PATH=data/team-config.json
```

В главном меню есть кнопки «Jira: проекты и отчёты» и «GitHub: запуск workflows», открывающие рабочие команды бота.

В меню настроек доступны:

- **Сотрудники:** добавление по Telegram ID или username, включение/отключение, связь с Jira по email, displayName или accountId. Числовые Telegram ID и Jira accountId предпочтительнее изменяемых имён.
- **Проекты Jira:** список ключей проектов. Назначение проекта сотруднику даёт доступ к нему и включает его worklogs в отчёты по этому проекту.
- **Ставки:** выберите сотрудника → «Ставки» → проект или «По умолчанию». Формат сообщения: `сумма валюта fixed|hourly [норма_часов]`. Например, `25 USDT hourly` или `100000 RUB fixed 80`. Изменяется только выбранная ставка; общая ставка и ставки других проектов сохраняются. `-` удаляет выбранную ставку: удаление проектной возвращает общую ставку. Ставка проекта имеет приоритет над общей, импортированной из env при первом запуске. В списке видны назначенные сотруднику проекты и уже настроенные проектные ставки. Общая фиксированная ставка начисляется один раз за выбранный спринт по совокупности назначенных проектов. При заданной норме часов фиксированная сумма пропорциональна отработанному времени, как и ранее.
- **Доступ к workflows:** конкретные разрешения каждому сотруднику; владелец имеет доступ ко всем. Отключение сотрудника сразу блокирует запуск, в том числе со старых кнопок.
- **GitHub workflows:** добавление, редактирование и удаление целей запуска. Формат: `owner/repository branch workflow.yml environment appType`. При изменении цели разрешения сотрудников отзываются и старые кнопки перестают работать, чтобы доступ к stage не превратился в доступ к prod.
- **Скачать конфиг:** приватная копия настроек, содержащая контакты и ставки, без API-токенов.

Изменения валидируются, атомарно сохраняются и действуют без пересборки или перезапуска. Незавершённый ввод можно отменить командой `/cancel`; время ввода — 10 минут. Бот рассчитан на один процесс, записывающий конфиг.

### Первый запуск и миграция

Если JSON-файл отсутствует, бот однократно импортирует `AVAILABILITY_BY_KEYS`, `RELATION_BY_NAME_OR_EMAIL`, `SALARY_RELATION_BY_TG_AND_PROJECT`, `GITHUB_WORKFLOW_SETTINGS` и записи из `SUPERADMIN_LIST`.

**Все импортированные сотрудники изначально отключены.** Откройте `/admin`, проверьте Jira-связи и проекты, включите только работающих сотрудников и выдайте нужные разрешения на workflows. Владелец всегда может открыть `/admin`, даже если его запись сотрудника отключена или отсутствует. Для включения собственных работ в отчёты нужна активная запись сотрудника с назначенными проектами.

После создания JSON старые переменные больше не управляют командой: деплой со старым env не восстановит уволенному сотруднику доступ. Повреждённый конфиг останавливает запуск; бот не заменяет его старым env. Храните резервные копии: удаление самого файла запускает импорт заново. Для восстановления остановите бот, замените файл сохранённой копией и запустите бот.

Отчёты включают только работы активных сотрудников в назначенных им проектах. Это ограничение действует и для владельца; обычный сотрудник видит только собственные работы. Период определяется временем выполнения worklog (`started`, при отсутствии — `created`).

### Деплой

В настройках GitHub репозитория один раз добавьте **Actions variable** `ADMIN_TELEGRAM_ID` со своим числовым Telegram ID. Секреты (`PRIVATE_ENV`, доступы к серверу и токены) остаются в Actions Secrets.

Workflow передаёт `.env` контейнеру при запуске, а не включает в Docker-образ. На сервере настройки лежат в `$HOME/nestjs-tg-jira-bot/data/team-config.json` и подключаются bind mount; пересоздание контейнера их сохраняет. Путь runtime env: `$HOME/nestjs-tg-jira-bot/bot.env`. Эти файлы не следует коммитить или публиковать как артефакты.

Деплой разрешён только владельцу исходного репозитория из `main`, включая проверку инициатора повторного запуска. При выдаче другим людям write-доступа защитите `main` и workflow от изменений без вашего участия: проверка в YAML не защищает от человека, который может переписать сам YAML.

Для локального Docker-запуска (env предварительно заполнен):

```bash
mkdir -p data
docker build -f Dockerfile-prod.api -t jira-bot .
docker run --name jira-bot -p 8080:8080 \
  --mount "type=bind,src=$(pwd)/data,dst=/usr/src/app/data" \
  --mount "type=bind,src=$(pwd)/.env,dst=/usr/src/app/.env,readonly" jira-bot
```

Проверки: `pnpm test --runInBand`, `pnpm run build:prod`.

### Github Sync by Webhook and Action
Бот умеет синкаться с Github через вебхук и Action.
Пример Action лежит в workflows_example/pull-request-created.yml.
В вашем проекте нужно создать соответствующий vars.JIRA_PUSH_BOT_ENV, с телом:
```
JIRA_BOT_HOST=ваш хост
JIRA_BOT_SECRET=ваш секрет для вебхука
```

Так же требуется прописать его в ваш .env в для бота.
